# meridian-ux.github.io

The marketing / main site for **meridian-ux** — *the declarative, cross-modal
console UI framework*. One descriptor proto (a form, a table, a command palette,
a conversation) renders natively in the browser, in a SwiftUI app, in the
terminal, and in wasm — re-skinned per tenant via `meridian.theme.v1`.

Astro (static), built hermetically on **Bazel 9** via
[`tomato-bazel/rules_astro`](https://github.com/tomato-bazel/rules_astro) — the
**same framework as `fastverk/site` and `tomato-bazel/site`**, re-skinned to the
meridian identity (cool azure → violet; the refracted-light **M** mark from
[`meridian-ux/brand`](https://github.com/meridian-ux/brand)).

🌐 **Live on GitHub Pages:** https://meridian-ux.github.io

## Feature-as-code

Each renderer owns its marketing metadata as a `fastverk.site.v1.Feature`
(`proto/fastverk/site/v1/feature.proto` — the schema is shared across the site
family). Seed protos live under `features/*.textproto`; the collector aggregates
them:

```
features/*.textproto  ──tools/collect_features.py──▶  src/content/features.json
                                                          │
                     /features (index of all)  ◀──────────┤
                     /features/<slug> (one page each: own hero + full <head>)
```

## Develop

pnpm install
# regenerate the catalog (needs protobuf on the interpreter):

## Manifest-generated conformance

`node tools/sync_conformance.mjs` resolves the public `meridian-ux/meridian`
main branch to an immutable SHA and imports its canonical
`schemas/conformance/coverage.json` into `src/content/coverage.json`, alongside
generated source provenance. Every deploy refreshes this snapshot before the
offline Astro build. Import failure stops the build; it does not silently publish
stale fallback data. The checked-in snapshot keeps local and Bazel builds
reproducible without network access during rendering.

`/conformance` derives every panel, conversation, and launchpad cell directly
from that manifest. It exposes reasons and waivers and distinguishes unverified
previews from declared rendering. The site smoke test verifies every emitted
cell and its exact status. For a verified local checkout, import offline with:

```bash
node tools/sync_conformance.mjs --manifest /path/to/meridian/schemas/conformance/coverage.json --revision FULL_COMMIT_SHA
node --test tools/sync_conformance.test.mjs
pnpm build
node tools/smoke_test.mjs
```

PR validation builds and tests without deploying. The existing main-branch
workflow still deploys GitHub Pages; merging a site PR therefore needs deployment
authorization in addition to normal review/CI approval.

## Deploy — GitHub Pages

Served as the **organization site** at `https://meridian-ux.github.io`. That only
works because the repo is named `<org>.github.io` — under any other name GitHub
Pages serves a *project* site at `/<repo>/` and the bare domain 404s, which is
exactly what it did until 2026-07-27. There is therefore **no `base`**, and links
and assets are plain absolute paths.

Every push to `main` runs [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml)
(Astro build → `actions/deploy-pages`); enable Pages with **Source =
GitHub Actions**. The workflow deliberately passes no `package-manager:` input —
`package.json` `packageManager` is the single pnpm declaration, and supplying both
makes `pnpm/action-setup` hard-error on the duplicate.

For a custom domain, set `site: "https://<domain>"` in `astro.config.mjs` and add
a `public/CNAME`. If you ever reintroduce a `base`, note that
`src/styles/global.css` references fonts by absolute `url()` and cannot read
`import.meta.env.BASE_URL` — the prefix has to be threaded through the CSS by
hand, which is why the old `/site` prefix was hardcoded in 28 places.

## Generated library references

The Astro site renders checked-in API snapshots from the same published
`0.25.1` npm packages used by the web quickstart. Each library page
uses the same declaration component. The React page additionally groups the
components, provider contracts, hooks, kits, and kit slots.

Regenerate from the site root. Use an external tools directory so these
dependencies do not change the site lockfile.

```sh
tools_dir=$(mktemp -d)
npm install --prefix "$tools_dir" --no-save --ignore-scripts --legacy-peer-deps \
  typescript@5.6.2 \
  @savvifi/meridian-web-react@0.25.1 @savvifi/meridian-mui-kit@0.25.1 \
  @savvifi/meridian-chat@0.25.1 @savvifi/meridian-launchpad@0.25.1 \
  @savvifi/meridian-proto-ts@0.25.1 @savvifi/meridian-schemas@0.25.1
node tools/gen-react-reference.mjs "$tools_dir/node_modules"
node tools/gen-library-references.mjs "$tools_dir/node_modules"
```

Pass `--check` as the final argument to either generator to verify that its
checked-in snapshot matches the installed declarations. Update the quickstart pins
and generation inputs together when changing the documented SDK version.

## Renderer gallery

GitHub Pages checks out the immutable Meridian revision in
`tools/meridian-revision.txt`. It uses that checkout for the WASM renderer,
the conformance table, and the protobuf fixtures. Before Astro builds, the
gallery preparer exercises every fixture at two widths and writes both the
browser assets and the text fallbacks. Generated files under
`public/tui-preview/` are build outputs.

To build the same gallery locally, install Node.js 22, pnpm, protoc, Rust
1.95.0, and wasm-bindgen CLI 0.2.105. Check out the pinned revision in a separate
Meridian checkout, then run from this repository:

```bash
pnpm install --frozen-lockfile
rustup target add --toolchain 1.95.0 wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.105 --locked
RUSTUP_TOOLCHAIN=1.95.0 bash tools/build-tui-preview.sh /path/to/meridian
node tools/sync_conformance.mjs --revision "$(cat tools/meridian-revision.txt)" \
  --manifest /path/to/meridian/schemas/conformance/coverage.json
pnpm build
MERIDIAN_REQUIRE_TUI_ASSETS=1 node tools/smoke_test.mjs
```

Each example has a stable fixture ID and a shared preview component. The
renderer registry can select an interactive terminal, an image capture, or
a placeholder, so a future native capture can use the same fixture pages.

### SwiftUI captures on macOS

The Pages workflow runs the capture on a GitHub-hosted macOS runner and passes
the resulting PNGs to the Astro build as an artifact. It reuses cached captures
for the same Meridian revision and capture code. Update
`tools/meridian-revision.txt` when the renderer or upstream fixtures change.
The Pages build verifies that every fixture embeds its corresponding PNG.

Use a clean Meridian checkout at the revision in
`tools/meridian-revision.txt`. Prepare its Swift package using Node.js 22, the
repository’s pinned pnpm, Xcode 26.2 or later, and stable Rust.

```bash
cd /path/to/meridian
pnpm install --frozen-lockfile --ignore-scripts
rustup target add aarch64-apple-darwin x86_64-apple-darwin \
  aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios
python3 tools/swiftui.py --generate-only

cd /path/to/meridian-ux.github.io
bash tools/capture-swiftui.sh /path/to/meridian choice form stat
bash tools/capture-swiftui.sh /path/to/meridian
```

The capture runs a temporary XCTest from the existing fixture harness and
removes it afterward. It draws each panel in a 640 × 480 point AppKit host
at 2× scale in light appearance. The revision in the image path ties it
to the corresponding terminal fixture. The pinned SwiftUI view projections
identify actual renderer placeholders. Local captures go under
`public/captures/swiftui/<revision>/`. Pages generates its own copies.
The Table capture replays the canonical populated response through the
SwiftUI host and checks that the fixture rows appear before saving the PNG.
The Form capture uses the same host seam to prefill a sample navigation
group and verifies that the nested add controls appear.
